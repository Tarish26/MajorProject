Introduction Modern web applications often require frequent UI updates to accommodate new data sources, KPIs, or features. However, hard-coding these changes increases development time and reduces flexibility. A  config-driven dashboard  allows developers or administrators to control what data, layout, and components appear on the dashboard through a simple configuration file (e.g., JSON), without altering the source code. This project aims to design and develop a  Config-Driven Dashboard  that dynamically renders cards, charts, and tables based on configuration files. It enables easy customization, modularity, and scalability — ideal for analytics and administrative use cases.
------------------------
Slide: ppt/slides/slide4.xml
Problem Statement In traditional frontend applications, updating UI elements (like adding charts or rearranging components) requires manual code modifications. This leads to: Increased development and deployment time. High maintenance cost for minor UI changes. Poor scalability when dashboards must vary for multiple users or departments. Hence, there is a need for a  config-driven system  where UI layouts and data sources can be easily managed through configuration files rather than code changes.

Key Design Decisions: Config-Driven UI:  The entire dashboard layout and content are defined by a JSON configuration object ( DashboardConfig ), enabling dynamic rendering without code changes. Separation of Concerns:  Decouples the Definition (Config) from the Presentation (Components), allowing runtime flexibility. Scalable Component Factory:  A central  DashboardComponent  iterates over the config and dynamically hosts specific card types (Metric, Chart, Table). Data Flow Logic: Single Source of Truth : The  DashboardService  holds the state in a  BehaviorSubject , ensuring all components see consistent data. Reactive Updates : Dashboard View : Subscribes to config$ observable to render the layout. Card Editor : Uses  Angular Signals  ( toSignal , computed) to derive instant preview states from form inputs. Immutable Actions : Updates are processed via pure functions in the service, emitting new state references to trigger change detection only when necessary. Project Design  (cont…) Module Interactions: Core Module : Contains singleton services ( DashboardService ) and data models ( DashboardConfig ). Loaded once at app startup. Features Modules : DashboardModule : Consumes config to render the view. CardEditorModule : Consumes config to provide editing capabilities. Shared Module : Provides reusable UI atoms (Buttons, Inputs) and Pipes (Formatters) to both feature modules, ensuring visual consistency. Key Algorithm: Dynamic Style Injection Sanitization : The  CardStyles  interface acts as an allowlist. Application : Styles are applied via  Angular's  [style] binding (e.g., [ style.gridColumn ]), preventing XSS risks while allowing user customization.
